Loom Core Agent Harness 架构设计

一个面向美股市场研判的 managed-agents 架构：Loom core agent 作为策略 brain， content agents 作为执行 hands，harness 负责基于 human-agent 交互进行策略选择、策略优化、资源治理与反馈学习。

版本：v1.0 日期：2026-05-28 领域：US Equities Research Agent 核心原则：Brain / Hands / Session / Harness 解耦

1. 设计结论

推荐采用 Event-Sourced Adaptive Harness：Loom core agent 不直接承担具体研究内容， 而是作为策略脑，围绕用户交互、资源信誉、分析策略、内容 agent 产物质量和用户反馈进行持续 harness。

content agents 负责具体工作，例如大盘、标的基本面、新闻归因、技术指标、期权情绪、KOL 叙事、买卖逻辑正反博弈等。 Loom core 通过统一任务接口调度它们，再对结果进行证据整合、冲突处理、置信度校准和面向用户的策略性输出。

关键边界：Loom core 是 meta-harness brain，不是内容生产者；content agents 是可替换的 worker hands，不是长期记忆拥有者； session/event log 是独立状态层，不绑定某一次模型上下文窗口。

2. 抽象原则映射

抽象 在本架构中的角色 设计要求
Brain Loom core agent 只负责策略选择、调度、评估、反馈编译和策略优化。
Hands Content agents 通过统一 execute(agent, envelope) 接口执行具体研究任务。
Session Interaction/event ledger 保存交互、策略、调用、证据、反馈、配置变更和 thesis 状态。
Harness Evaluation + resource + policy + feedback loop 不写死 workflow，但写死质量契约、反馈转化规则和安全边界。
Tools / Resources 数据源、新闻源、KOL、技术指标、外部平台 通过资源注册表和信誉分动态选择，不隐式成为事实依据。

4. 核心组件

Loom Core Agent

负责理解用户意图、选择分析策略、调度 content agents、合并结果、检测冲突、生成最终输出，并把用户反馈转为可审计的策略更新。

Content Agents

负责具体内容工作。它们可以内部推理，但对 Loom core 来说必须像工具一样可调用、可替换、可评估。

Session Event Log

保存人类输入、agent 输出、策略选择、任务调用、证据、反馈、资源升降权和 thesis 状态。

Resource Registry

管理信息平台、数据源、新闻源、KOL、技术指标来源，记录用途、层级、时效、冲突规则和历史表现。

Evaluation Harness

评估 content agent 产物质量：事实性、证据充分性、冲突展示、来源合规、时效性、对用户偏好的贴合度。

Policy Gate

金融场景安全边界：不直接给买卖指令，必须区分事实、解释、推测，弱来源不能覆盖官方数据。

5. Loom Core 职责边界

Loom core 应该负责
  • 识别用户当前意图和时间尺度。
  • 选择本轮分析策略和 content agents。
  • 分配资源预算和可信来源优先级。
  • 整合 claims、evidence、counter-evidence。
  • 处理来源冲突和置信度校准。
  • 把用户反馈编译为策略、资源、权重调整建议。
  • 维护 thesis 的确认、削弱、推翻状态。
Loom core 不应该负责
  • 直接抓取所有行情、新闻和原始数据。
  • 亲自计算所有技术指标。
  • 硬编码 KOL 列表或新闻平台优先级。
  • 把社交媒体或 KOL 观点当作事实依据。
  • 在未确认时静默修改长期用户偏好。
  • 直接输出“应该买入/卖出”的指令式建议。

6. Content Agents 设计

Agent 职责 典型输入 典型输出
Market Regime Agent 分析大盘环境、利率、流动性、信用、波动率、宏观事件。 市场、时间尺度、关注指标、来源政策。 市场状态、驱动因素、冲突信号、推翻条件。
Sector Rotation Agent 识别板块轮动、相对强弱、资金流、盈利修正和行业景气。 板块列表、市场状态、近期事件。 领先/落后板块、轮动判断、资金确认。
Ticker Fundamentals Agent 跟踪核心标的基本盘、财报、预期差、估值、竞争格局。 ticker、用户 thesis、财报窗口。 基本面 claims、证据、风险、数据缺口。
Technical / Options Agent 分析趋势结构、成交量、关键位、期权、IV、拥挤度。 ticker、时间尺度、价格数据。 技术结构、期权情绪、触发位、风险提醒。
News & KOL Scout Agent 发现新闻归因、叙事变化和 KOL 观点，但只作为事实解释或假设生成。 主题、ticker、允许来源、排除来源。 事件摘要、叙事变化、弱信号、需验证假设。
Thesis Debate Agent 围绕用户买入/卖出/持有逻辑进行正反博弈追踪。 原始交易逻辑、持仓状态、新证据。 bull/bear case、假设变化、推翻条件状态。
Source Discovery Agent 根据任务寻找可加入资源注册表的新平台、新数据源、新 KOL。 信息缺口、用户反馈、现有资源表现。 候选资源、用途、风险、建议 tier。

7. 统一任务接口

Loom core 调度 content agents 时不发送模糊指令，而是发送结构化任务信封。 这样 hands 可以扩展，但 brain 的调用方式稳定。 

interface TaskEnvelope {
  task_id: string;
  agent_name: string;
  objective: string;

  subject: {
    type: "market" | "sector" | "ticker" | "thesis" | "resource";
    ticker?: string;
    sector?: string;
    theme?: string;
  };

  user_context: {
    horizon: "intraday" | "days" | "weeks" | "quarters";
    current_thesis?: string;
    known_preferences?: string[];
    watchlist?: string[];
  };

  required_output: Array<
    "claims" |
    "evidence" |
    "counter_evidence" |
    "freshness" |
    "confidence" |
    "reversal_conditions" |
    "data_gaps"
  >;

  resource_policy: {
    allowed_tiers: Array<"A" | "B" | "C" | "D" | "E" | "F">;
    preferred_sources?: string[];
    excluded_sources?: string[];
    kol_usage: "hypothesis_only" | "sentiment_only" | "disabled";
  };
}

统一返回产物

interface AgentArtifact {
  task_id: string;
  agent_name: string;
  summary: string;
  claims: Claim[];
  evidence: Evidence[];
  counter_evidence: Evidence[];
  source_usage: SourceUsage[];
  confidence: number;
  freshness: "live" | "recent" | "stale" | "unknown";
  gaps: string[];
  recommended_next_tasks: TaskSuggestion[];
}

8. Session / Event Log

Session 是可恢复、可重放、可审计的事实来源。Loom core 不应该把长期状态只保存在模型上下文里， 而应该每次从 event log 中恢复必要切片。

图 2：每轮交互都以 event log 为中心，Loom core 可恢复、可重放、可替换。

9. Claim & Evidence Ledger

所有分析结论都先成为可追踪 claim，而不是只存在于自然语言回答中。 这是后续评估、纠错、反馈学习和 thesis 博弈追踪的基础。 

interface Claim {
  claim_id: string;
  subject: "market" | "sector" | "ticker" | "position_logic";
  ticker?: string;
  text: string;
  stance: "bullish" | "bearish" | "neutral" | "mixed";
  time_horizon: "intraday" | "days" | "weeks" | "quarters";
  confidence: number;
  evidence_ids: string[];
  counter_evidence_ids: string[];
  reversal_conditions: ReversalCondition[];
  status: "active" | "weakened" | "invalidated" | "confirmed";
}

10. Resource Harness

信息平台和 KOL 不应该写死在 workflow 里，而应该作为可学习、可升降权、可禁用的资源对象。 Loom core 负责对资源的使用进行 harness：用途是否正确、是否越权、是否被用户纠正、是否值得加入长期资源池。 

resources:
  - id: sec-edgar
    type: document_source
    scope: ticker
    trust_tier: A
    use_for: [filings, fundamentals, risk_factors]
    authority: fact_base
    conflict_policy: authoritative

  - id: reuters
    type: news_source
    scope: market
    trust_tier: C
    use_for: [event_attribution, breaking_news]
    authority: news_fact
    conflict_policy: corroborate

  - id: kol-example
    type: kol
    scope: macro_liquidity
    trust_tier: F
    use_for: [narrative_discovery, contrarian_view]
    authority: hypothesis_only
    conflict_policy: background_only
    performance:
      accepted_by_user: 0
      corrected_by_user: 0
      stale_or_noisy: 0
KOL 和社交来源默认只能用于假设生成、叙事发现或情绪观察，不能直接覆盖官方数据、公司披露或主流新闻事实。

11. Human Feedback Compiler

用户反馈不是简单追加到 prompt，而是被编译成结构化事件，再映射为可审计的策略、资源或配置调整。

用户反馈类型 结构化分类 Harness 动作
“这个事实不对” wrong_fact 检查来源；降低相关资源权重；要求 A/B/C 层来源确认。
“太依赖宏观了” too_macro_heavy 降低宏观权重；提高标的基本面或技术结构权重。
“这个 KOL 不靠谱” bad_kol_choice 将资源降权或标记为仅背景参考。
“这次反方说得有用” useful_counter_evidence 提升冲突证据展示权重；强化 thesis debate agent。
“以后总是帮我看流动性” preferred_dimension 提出 config patch，经用户确认后持久化。 
feedback_loop:
  human_feedback
    -> classify_feedback
    -> locate_affected_claim_or_resource
    -> propose_strategy_or_config_patch
    -> require_user_confirmation_for_durable_changes
    -> persist_patch
    -> use_next_session

12. Thesis Debate Harness

对用户买入、卖出、持有、观望逻辑，harness 不直接替用户决策，而是持续追踪该逻辑的正反证据和推翻条件。 

interface TradingThesis {
  thesis_id: string;
  ticker: string;
  user_intent: "buy" | "sell" | "hold" | "watch";
  original_logic: string;

  bull_case: Claim[];
  bear_case: Claim[];
  key_assumptions: string[];
  invalidation_triggers: string[];

  watched_dimensions: Array<
    "fundamentals" |
    "expectations" |
    "valuation" |
    "technical" |
    "options" |
    "macro" |
    "sector" |
    "sentiment" |
    "news"
  >;

  debate_state: {
    bull_score: number;
    bear_score: number;
    uncertainty: number;
    last_reviewed_at: string;
  };
}

新信息进入时，Thesis Debate Agent 只回答：它支持原始逻辑、削弱原始逻辑、构成噪音，还是触发了推翻条件。 这样用户可以稳定追踪自己的判断质量，而不是被每条新闻带着走。

13. Analysis Contract

不写死 workflow，但必须写死输出质量契约。Loom core 可以自由选择策略和 hands，但最终输出必须满足以下要求。 

analysis_contract:
  required:
    - conclusion
    - claims
    - evidence
    - counter_evidence
    - source_tiers
    - freshness
    - confidence
    - reversal_conditions
    - data_gaps

  rules:
    - facts_interpretations_and_speculations_must_be_separated
    - weak_social_or_kol_sources_cannot_override_official_or_vendor_data
    - missing_or_stale_data_must_be_labeled
    - high_confidence_claims_require_strong_source_support
    - direct_buy_sell_instruction_is_disallowed
    - conflict_resolution_must_be_explicit

14. 最小可行实现

  1. Resource Registry：先把已有 connectors、新闻源、KOL、指标来源注册起来。
  2. Claim Ledger：让每次分析输出结构化 claim/evidence/counter-evidence。
  3. Task Envelope：统一 Loom core 调 content agents 的接口。
  4. Feedback Compiler：把用户反馈转为分类、影响对象和 config patch。
  5. Thesis Debate Tracker：围绕用户买卖逻辑持续记录正反证据和推翻状态。
  6. Policy Gate：先实现最重要的金融安全与来源层级规则。
第一版不要让系统自动大幅修改长期策略。建议采用“反馈累计 -> patch 提案 -> 用户确认 -> 持久化”的节奏。

15. 关键架构决策

决策
Loom core 只做策略脑，content agents 做执行手。
理由
降低耦合；便于增加新信息源、新分析维度、新 agent；也便于单独评估每个 content agent 的质量。
代价
需要定义清晰的任务接口、产物格式和评估规则。
缓解
使用统一 TaskEnvelope 与 AgentArtifact，并让所有产物进入 Claim Ledger。
决策
Session 独立于 Loom core 的模型上下文。
理由
支持恢复、回放、审计、长期反馈学习和模型替换。
代价
需要事件 schema 和状态重建逻辑。
缓解
从最小事件集开始：question、strategy、agent call、artifact、claim、feedback、patch。
决策
资源选择由 Resource Harness 管理，而不是写死在 workflow 中。
理由
信息平台和 KOL 的价值会随市场、用户偏好和历史表现变化。
代价
资源需要元数据和评分。
缓解
先记录 tier、use_for、conflict_policy、用户反馈计数，再逐步加入自动评分。

16. 风险与缓解

风险 影响 缓解策略
Loom core 重新变成大而全 agent 难评估、难扩展、难替换。 严格限制 Loom core 职责，只允许它调度、整合、评估和学习。
content agents 输出自然语言不可审计 无法追踪错误来源和反馈影响。 要求所有 agents 返回结构化 AgentArtifact。
KOL 或社交来源越权 弱信号被误当事实依据。 资源注册表声明 authority；Policy Gate 阻止弱来源覆盖强来源。
用户反馈被过度拟合 系统因单次反馈产生不稳定偏好。 区分 session-level adjustment 与 durable preference；长期变更需要用户确认。
自动策略优化不可解释 用户不知道为什么 agent 改变分析方式。 所有 config patch 以事件记录，并展示“为什么调整”。
本文档为 Loom Core Agent Harness 架构设计稿。核心目标是让市场研判 agent 在 human-agent 交互中持续学习， 但保持证据可追踪、资源可治理、策略可审计、输出有边界。
