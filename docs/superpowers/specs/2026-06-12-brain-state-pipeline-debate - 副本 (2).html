Loom Brain · 渐进式架构

从三个盒子讲起：Brain 怎么编排 Hand 完成任务

把方案展开成 7 个递进的 Level。每一层只新增 1–2 个概念，每个概念先一句话定义、再说它解决什么问题、最后列出它的能力或维度。 读者读到任何一层都能停下来，因为下一层不会推翻前一层。

Level 0 · 一句话

这个系统到底在干什么？

Brain 接到一个用户问题 → 拆成几个小任务交给 Hand 去做 → 把 Hand 的结果合成一份带证据的判断返回。 所有"跑过什么"的痕迹都住在 State 里，下一次还能用。

接下来每一层都只在这张图上加一点东西，不替换它。

Level 1 · 最小骨架

三个盒子：Brain、Hand、State

Brain编排者
→
Hand × N执行者
↻
State共享档案

是什么 Brain

项目经理。读问题、定计划、挑人、收成果、写综述。不直接干活。

是什么 Hand

具体执行者，一个 原子任务 的执行壳。Hand 不按 domain 划分（"市场"不是 hand 颗粒度），而是按"能独立交付一个明确子问题"为单位。 例："取过去 5 天 VIX 序列并判断趋势"、"读这家公司最新 8-K 找重大事件"、"比较 SOX 行业当前 PE 在 5 年分位中的位置"。 不做全局综合判断——综合归 Brain。
原方案缺口 当前 loom/hands/{market,sentiment,target,position}.py 太粗， "market hand" 实际包揽了宏观、流动性、广度、轮动、催化五件事。L10 会拆开它。

是什么 State

共享档案室。所有跨次数、跨任务可复用的信息住在这里：规则、框架、过往结论、用户偏好。Brain 写完综述把 state 更新一下，下次开局就能用。

代码里已经存在的对应物：LoomCoreAgent（Brain）、loom/hands/（Hand）、BrainState + GoalContext + IntentWiki + Flywheel（State 的多张面孔）。

Level 2 · 一次任务

"跑一次任务"具体经历什么

一次任务的全部经历 = 一个 Episode。它是 Brain 处理某个问题的完整记录，从问题进来到结论出去。
① 计划
→
② 派活
→
③ 验收
→
④ 综合
→
⑤ 存档

四个主流程（Brain 已经具备的雏形）

  1. 计划 Plan：Brain 读问题，写下"这次要看哪些维度"（rubrics）。
  2. 派活 Dispatch：Brain 选 N 个 Hand，把任务和验收维度一起交出去；Hand 并行执行。
  3. 验收 Review：Brain 收回 hand artifacts，按 rubric 检查覆盖度；缺的派"修复 Hand"。
  4. 综合 Synthesize：Brain 写出最终结论（stance / confidence / reversal / watch）。

新增概念 Episode（一次任务记录）

把上面五步之中发生的所有事件串成一条只追加的事件日志，存为一个文件：brain/episodes/<episode_id>.jsonl。 事件类型包括 phase.start / dispatch.sent / dispatch.artifact / review.flag / synthesis.partial / state.checkpoint 等。 Episode 让任务变成可暂停、可恢复、可回放的对象，而不是一次性函数调用。

① ② ③ ④ ⑤ 之间不是严格线性。比如 ③ 发现缺口可以回到 ②；用户在任何点都可以中断。 所以底层用事件驱动的状态机实现，外层呈现成五个步骤只是为了讲清楚。
Level 3 · State 维度

State 里都装些什么？

把"跑一次任务的所有变量"分成三圈：核心圈（每个 Episode 必有）、增强圈（让方案更稳健）、长期圈（跨 Episode 累积）。 原 spec 只覆盖了核心圈的一半，本节把缺的补齐。

核心圈 · 没有它跑不起来（6 项）

目标 Goal用户到底想要什么；包括 success_criteria、deadline、优先级。用例：判断什么时候算"做完了"。
验收维度 Rubrics这次要看的几个面（如"宏观、估值、催化"），每个面有 requirements / acceptance。用例：让 Hand 知道要交什么样的料；让 Brain 知道验什么。
Hand 派单 Hand Spec本次具体派哪些原子任务、每个 Hand 拿到的精确子问题、绑定的 Adapter、只暴露给它的 state 切片（不全暴露）。用例：替代粗粒度的"domain → 固定 4 个 Hand"映射。
执行轨迹 Trace事件日志：每个阶段什么时候开始结束、哪个 dispatch 发了什么、收到什么。用例：失败恢复、debug、replay。
缺口 Quality GapsReview 时发现的覆盖不全、证据陈旧、置信偏低、互相冲突的地方。用例：触发修复 Hand；告知用户哪里不确定。
输出 Synthesis + Data Product最终结论 + 一个版本化、可被外部消费的结构化数据负载。用例：UI 渲染、自动化下游消费。

增强圈 · 让方案稳健的关键 4 项

能力清单 Capability Inventory规划时刻快照：哪些 Adapter 可用、各自模型/工具/上下文上限/单调成本/p50 延时/信任档位。用例：HandPlanner 选 Hand 时按能力匹配，而不是按 domain 表。
预算 Budgettoken / 成本 / 墙钟 / 截止时间；可分到 per-dispatch、per-phase。用例：防止单个 Hand 把整个 Episode 吃光；触线即提前转 Synthesizing。
上下文 Context Packet这次注入给每个 agent 的内容指针：rule_ids / framework_ids / 最近 intent / 上次综述哈希。用例：用最小注入达到最大效果；预算压力下知道丢什么。
证据信任 Evidence & Trust每条 claim 的 source / source_tier / freshness / confidence / hand_id / rubric。用例：跨 Hand 互证、冲突识别、信任分级。

长期圈 · 跨 Episode 累积的 3 项

世界快照 World State规划时刻冻结的市场时钟、连接器健康、数据源新鲜度。用例：保证 replay 可复现；区分"信息错"和"世界变了"。
用户介入 User Interventions用户的编辑、锁定、拒绝、纠正；以及 Brain 主动求决的位置。用例：喂给 CorrectionDetector；持久 Hand 晋升的否决权。
分支 Branch同一 goal 下的 what-if、A/B framework；先预留字段不启用。用例：未来支持探索性分析不破坏 schema。
读法：L4 之后所有"加层"动作，都对应给上面 13 项中的某一项加内容。所以读到这里就已经看到方案的全部 state 面貌了；后面只是给它们加机制。
Level 4 · Adapter

Hand 是异构的：用 Adapter 屏蔽差异

Brain 不应该关心"这个 Hand 是 Claude 还是 GPT 还是本地 Llama"。中间加一层 Adapter，所有 Hand 长成同一个样子。 这是让方案"通用"的核心机制。
Brain
→
Adapter统一接口
→
Hand AClaude API
Hand BSDK 循环
Hand C本地 Llama

是什么 Adapter

"中介公司"。Brain 不直接联系员工（LLM），而是把任务交给中介，中介负责跑通底层差异。 Adapter 暴露的接口固定：invoke(envelope) → AsyncIterator[event]。无论后面挂的是闭源 API、SDK 循环、还是开源模型，对 Brain 来说看到的都是同一种事件流。

为什么需要 通用性 = 协议 + 能力位

三类 Hand 能力天然不同：闭源 API 没办法做 bit-精确重放；开源模型可以。 Adapter 的方案是：所有 Adapter 实现同一个接口，但额外声明一个 capabilities 字典，告诉 Brain "我支持什么"。 Brain 优先用强能力，缺时优雅降级。

Adapter 在仓库里已经存在的雏形

翻代码：loom_core/agent_adapters/providers/ 下已经有 6 个 provider： cc / codex / herms / opencode / openclaw / sdk_legacy。 sdk_legacy.py::InProcessAdapter.invoke() 就是上面所说的契约。所以这一层不是新建，是规范化和补全能力声明。

Level 5 · 治理与修复

把"会失控的循环"治住

没有治理的话，Brain 可能调用 Hand 直到把 token 烧光；Hand 可能返回 schema 不对的垃圾还被采用；Repair 可能死循环。 在 dispatch 周围加 三个闸门。
Brain
→
① 预算闸Budget Governor
→
Adapter
→
② Schema 闸jsonschema 校验
→
Brain（收）

闸 ① Budget Governor

监听事件流的 token_delta / completed，按 episode / phase / dispatch 三级累加。 超阈值即抛 BudgetExceeded，Brain 收到后提前进入 Synthesize，把缺口写入 quality_gaps，不要让用户什么都看不到。

闸 ② Schema 校验

每个 run.artifact 必须先通过 jsonschema 校验才允许写入 state。 不通过的话，触发一个修复 dispatch，把违规细节当作 feedback 回传，而不是 raw retry。

闸 ③ Repair Termination

修复 dispatch 也吃 budget，并受最大迭代次数限制。repair_budget_remaining = 0 时停止修复， 把残留缺口落到 quality_gaps 让用户看见。放弃修复也是合规结果，不是隐式失败。

Level 6 · 复用与对外

把"反复用得到的东西"沉淀出来

Hand 有两种生命周期：Runtime（一次性，跟 episode 走）和 Persistent（沉淀到磁盘、给固定任务复用）。 此外，把对内对外的两种调用路径分开。

Hand 生命周期

  • Runtime Hand：日常通用任务的默认路径。每次 Brain 为子任务临时生成 spec，绑定到已有 Adapter，跑完只留事件日志，不写长期目录。
  • Persistent Hand：固定任务域（如 loom-fin 市场研判、仓位管理）才允许。需要过晋升门才能落盘到 brain/hand_specs/<domain>/<hand_id>.json。

是什么 持久 Hand Spec 的字段

hand_id / base_hand_id / version / owner_domain / task_template / capabilities / rubrics_default / acceptance_default / created_from_episode / created_at / last_eval_ts / eval_score / deprecation_status

是什么 晋升门（runtime → persistent 的四个条件）

(a) domain 主权认领；(b) 持出测试集 eval 达标；(c) 创建 episode 的 user_interventions 未否决该 artifact；(d) 成本和延时在预算内。 四条不全则不允许落盘。

两种对外路径

路径用户返回用途
POST /analyze UI（webview） 带 presentation 的渲染包 正常交互，看得见的卡片、drill-down
POST /brain/runs
GET /brain/runs/{id}		 脚本、定时任务、移动端 纯 JSON data_product.v1 固定任务、headless 自动化

两条路径共享同一个 LoomCoreAgent pipeline，避免出现双轨逻辑。

是什么 brain.data_product.v1 schema

放在 brain/schemas/brain.data_product.v1.json。字段： version / episode_id / goal_id / synthesis / evidence[] / quality_gaps[] / watch_conditions[] / regime_relevance / produced_at / expires_at。 Headless API 返回前必须先过 schema。UI 渲染就变成"读 data_product 渲染卡片"的纯函数。

Level 7 · 审计与重放

所有事都可以倒回去

事件日志是只追加的；把日志重新喂回 orchestrator（但不调真实 Adapter）就能重放任意一次 episode。 闭源 / SDK 退化到"input-equal"重放，开源支持 bit-exact 重放（多存了 seed）。

能用 Replay 干什么

  • Debug：定位某次综述里某条 claim 是从哪来的。
  • 回归测试：方案修改后跑历史 episode，看综述是否退化。
  • 微调数据：高质量 episode 直接当训练样本（带 reversal/watch 的对比标签）。
  • Eval：晋升门用的 eval 数据集就是过往合格 episode 的子集。

并发与崩溃恢复

  • 同一 goal_id 写 GoalContext.synthesis_history 时一把写锁；不同 goal 自由并发。
  • 事件日志只追加；最近的 state.checkpoint 是恢复点。
  • 进程重启：扫描 brain/episodes/，对最后事件不是 Persisted | Failed 的 episode 走恢复或标 Failed。
Level 8 · 反馈回流

跑完之后，反馈会回写到 state 的哪里？

Episode 跑完不是终点。反馈信号会从 episode 里抽出来，回写到长期 state，下一次跑就用得上。 所以这一层回答：哪种反馈 → 影响哪个 state 维度 → 改变后续什么行为。

两种 rollout 路径产生的反馈不同

路径典型场景反馈源
Automatic Harness Rollout
/brain/runs		 定时跑批、固定任务（如每日盘前研判）、外部脚本调用 事后客观验证：预测 vs 实际、缺口比例、连接器健康、成本/延时
Human-Agent 协作 Rollout
/analyze + UI		 用户在 webview 里 refine / lock / branch / 编辑卡片 主观信号：用户接受/拒绝、纠正内容、停留时长、二次提问

五类反馈信号 · 各自回写到哪

信号 ① 预测 vs 实际

来源：automatic rollout 的事后比对（如 reversal 条件命中、watch 条件触发、置信度校准）。
回写： persistent_hand_spec.eval_score（影响晋升门）+ BrainState.frameworks[].confidence（高/中/低/未检验四档）+ RewardedIntentHarness.reward_report（喂飞轮）。
后续影响：低分 hand 自动降级，不再被 HandPlanner 优先挑选；低 confidence 框架在 prompt 里降权或剔除。

信号 ② 用户纠正与拒绝

来源：human-agent 协作中的 edit / reject / lock / annotate 事件。
回写： episode.user_interventions[]（即时）→ IntentWiki.activation_history（汇总意图模式）→ CorrectionDetector 产出的 turn-pair（喂训练 / 微调数据）。
后续影响：同类问题再来时，IntentWiki 注入"用户上次拒绝过 X、偏好 Y"；持久 Hand 晋升门一票否决。

信号 ③ 矛盾与冲突

来源：Review 阶段发现的 hand 间冲突、或后续 episode 推翻前次结论。
回写： GoalContext.contradiction_log（持久于 goal 维度）+ BrainState.notes（在 domain 维度生成 learned_note，标注冲突来源）。
后续影响：规划阶段读到同 goal 有未解冲突时，主动加 rubric 维度去验证；冲突未解的综述自动降置信度。

信号 ④ 覆盖率 / 缺口模式

来源：跨 episode 聚合的 quality_gaps 统计（"过去 10 次都缺 catalyst 维度"）。
回写： domain 默认 rubrics_template 加新维度 + connector quality registry 标记哪些源经常缺/过期。
后续影响：下一次同 domain 任务默认就带这个 rubric；HandPlanner 选源时降权问题连接器。

信号 ⑤ 性能与成本观测

来源：所有 episode 的 budget、p50_latency_ms、cost_per_call 实测。
回写： capability_inventory.adapters[*] 的实测档位（覆盖配置档位）。
后续影响：HandPlanner 在两种 adapter 等效时，按实测成本/延时挑选；预算闸的阈值随实测分布调整。

Level 9 · 资源与 Wiki

用户每天塞进来的资源、wiki 住在框架的哪一部分？

用户传入的信息分三种来源：连接器 Connector（自动拉的 RSS/API）、Inbox（用户手动塞的条目）、 Wiki（用户长期沉淀的偏好和规则）。它们在框架中各自占据一个位置，彼此分工清楚。

三种来源 · 三种角色

Connector 自动连接外部数据源（RSS / SEC EDGAR / FRED / Finnhub / KOL feed）。 代码：loom/bridge.py::get_connector_data()、mcp/connectors/
Inbox 用户手动塞进系统的东西：新闻链接、截图、文档、临时观察。 代码：mcp__anchor__anchor_inbox_*
Wiki / Intent 用户长期沉淀：偏好（如"我只关心半导体"）、自定义规则、个人 framework。 代码：BrainState.rules / frameworks / notes、IntentWiki、intent_stream.jsonl

它们怎么参与到一次 Episode

入口 ① 规划阶段：进入 Capability Inventory + World State

Connector 在规划时刻被枚举，每个 connector 的健康度、最近一次拉取时间、tier 档位写入 capability_inventory.resources[] 和 world_state.connector_health。
用例：HandPlanner 选 Hand 时知道"finnhub 现在响应 5 秒、Tier B"，会调整 rubric 验收策略。

入口 ② 派发阶段：进入 Context Packet

Inbox 中和当前问题相关的条目（按域过滤）注入到 hand context：context_packet[hand_id].inbox_refs[]。 Hand 在执行时可以 fetch_resource 取详情。
用例：用户中午塞了一篇 SEC 8-K，下午做研判时这个文档会出现在 target hand 的 context 里。

入口 ③ 派发阶段：进入 Prompt 注入

Wiki / IntentWiki 是结构化注入而非全量加载（既有 BrainHarness._assemble_prompt 已经实现： query_rules(domain) / query_frameworks(domain) / intent_stream.tail(5) / query_notes(domain)）。
用例：用户长期偏好"先看流动性再看估值"被解析成一条 rule，规划阶段只有该 rule 命中 domain 时才入 prompt。

入口 ④ 证据阶段：进入 Evidence 出处

当 Hand 引用一个 connector 或 inbox 条目作为支撑，evidence[].source 记录其 resource_id， source_tier 来自连接器配置，freshness 来自 world_state 里那时刻的快照。
用例：每条 claim 都能反查"来自哪条 RSS、当天几点拉的"。

用户更新 Wiki 的反向流程

  1. 显式：用户在 webview 写 rule / 加 framework → 直接落 BrainState 文件（带 frontmatter）。
  2. 隐式：用户的 inbox push 累积成 intent_stream.jsonl → IntentWiki 识别成意图 → RewardedIntentHarness 提炼出 PolicyPlan → distiller.py 把高反复出现的意图蒸馏成 framework / note。

所以 Wiki 不是一个新模块，而是"L3 的长期圈那三项 + 既有 BrainState/IntentWiki 文件"的统一称呼。

Level 10 · Hand 原子化

把 "market hand" 拆成它真正的样子

当前一个 MarketHand 包揽宏观、流动性、广度、轮动、催化五件事——这意味着 Brain 没真正的投研策略，只是把问题丢给 LLM 自由发挥。 正确的形态：Brain 持有投研策略，按 state 把任务拆成原子 hand task，每个 Hand 是一个"明确小问题 + 明确数据切片 + 明确产出 schema"。

原子 Hand Task 的四要素

  1. 一个精确的子问题（一句话能讲清，可独立判断对错）。
  2. 一份 state 切片需求（只暴露这个 task 真正用得到的连接器/inbox/wiki 项）。
  3. 一个工具子集（不暴露全部资源菜单）。
  4. 一个小 JSON 产出 schema（不要长 narrative）。

以 "market 研判" 为例：拆成的原子任务族

原子任务精确子问题需要的 state 切片典型执行 Hand

Brain 在 plan 阶段做什么

  1. 读 goal + intent + meta 策略 spec（见 L11）。
  2. 从原子任务库挑出本次需要的子集（不一定全派；按 budget 与 rubric 取舍）。
  3. 给每个原子任务绑定一个 base_hand_id（数据型/推理型/综合型），由 Skill Recommender（L12）决定。
  4. 为每个原子任务计算 state 切片 与 工具子集，最小化注入。
  5. 计算依赖图（如 valuation 依赖 macro_rates 的实际利率结论），串并行 dispatch。

新增对象 原子任务库 Atomic Task Library

放在 brain/atomic_tasks/<domain>/<task_id>.yaml。每个文件描述： task_id / domain / sub_question / state_slice_template / tool_subset / output_schema / recommended_skill_class。Brain 不再凭空想象任务拆分，而是从这个库里组合。

为什么这件事最关键：没有原子化，Brain 的"策略"全部塞给 LLM 当自由发挥。 原子化之后，Brain 的策略变成"选哪些原子任务 + 怎么排依赖 + 怎么暴露 state"—— 这正是可以学习、可以蒸馏、可以版本化的真正智能。
Level 11 · IntentWiki = Meta 策略

IntentWiki 的真实形态：从 KOL 推文蒸馏出的投研策略

用户长期看某 KOL 的推文（如 Lyn Alden、Howard Marks）不是"偏好"——是用户在给 Brain 灌输某套投研思路。 IntentWiki 的正确产出，是把这些数据蒸馏成 high-level 的策略 spec：rubric 模板、原子任务拆解套路、framework 调用顺序。 只有 high-level + spec 化，才能在 Brain 的 agentic 行为中发挥作用。

三层蒸馏

L0 行为信号 · Raw 用户的原始动作：inbox push（KOL 推文截图、SEC 文档、新闻）、KOL feed 订阅、reject / accept / lock 卡片、停留时长。 载体：brain/context/intent-stream.jsonl + brain/inbox/
L1 意图激活 · Activation 从 raw 信号识别出"用户最近关心半导体周期"、"用户偏好低估值高股息"、"用户对宏观因子敏感"等模式。 载体：brain/intent_wiki/intents.json + evidence.jsonl
L2 Meta 策略 Spec · Strategy 从大量 L0 + L1 数据蒸馏出的 投研策略 spec。 例：从 Lyn Alden 推文蒸馏出"先看真实利率 → 再看美元 → 再看新兴市场反应"的调用顺序， 以及"什么时候启用这套思路"的触发条件。 载体（新）：brain/strategy_library/<strategy_id>.yaml

Meta 策略 Spec 的字段（新结构）

  • strategy_id：唯一标识，如 lynalden-real-rates-em。
  • source：{kind: kol|self_correction|repeated_pattern, ref: 'lynalden.com/...', distilled_from: [evidence_ids]}。
  • domain：适用域（macro / equity / commodity / fx / fixed_income）。
  • triggering_conditions：什么样的 goal / 当前 state 命中此策略（如 "domain=macro AND state.regime contains 'rate_cycle'"）。
  • rubric_template：转化为本次 rubric 的模板（dimension + requirements + acceptance）。
  • atomic_task_decomposition：把高级问题拆成哪些原子 hand task（指 L10 库里的 task_id）+ 依赖顺序。
  • framework_refs：本策略调用的分析框架 id（指 BrainState.frameworks 中已存在的项）。
  • state_disclosure_policy：执行此策略时允许把 state 的哪些切片暴露给 hand。
  • confidence / last_updated / version / supersedes：版本与生命周期。

从 KOL 数据如何蒸馏出 Meta 策略（一个完整例子）

  1. 输入：用户过去 3 个月推送了 47 篇 Lyn Alden 的宏观推文 + 12 个 reject、3 个 lock 行为。
  2. L0 → L1：distiller.py 识别出主题聚类——"真实利率"、"美元周期"、"新兴市场流动性"反复出现。
  3. L1 → L2：进一步识别调用顺序——Lyn 总是按 "real_rates → USD → EM" 推理。 蒸馏出 strategy_id: lynalden-real-rates-em，写入 brain/strategy_library/。
  4. 使用：用户问"半导体最近能不能买"，Brain plan 阶段命中 triggering_conditions（domain=equity 但 state.regime 涉及 rates）。 调用此策略 → 生成 rubric（"必须包含真实利率维度"）+ 原子任务拆分（先派 macro_rates 与 liquidity，再派 sector_rotation，最后 valuation）。
  5. 反馈：本次 episode 结束后，用户接受/拒绝该综述会进一步更新此策略的 confidence。

Level 12 · Brain 是策略中心

能力沉淀在 Brain 侧：Hand 是薄壳

Hand 不应该是"自己想怎么干就怎么干的小 agent"。Hand = 接 envelope、按 schema 出 artifact 的薄壳。 所有可学习、可蒸馏、可版本化的能力都沉淀在 Brain 侧，作为 Brain 的"策略库 + 教练能力"。

Brain 侧 Harness 应包含的 7 项能力

能力 ① Goal Templating

把模糊用户问题归类成 GoalTemplate（如 market_research / position_review / target_tracking）， 每种 template 带默认 success_criteria 与 acceptance_policy。 载体：brain/goal_templates/<goal_type>.yaml。 用例：用户随口问"市场怎么看"会被映射到 market_research template。

能力 ② Rubric Library + Composer

常用 rubric 维度的可组合库（不是每次现编）。Composer 把 GoalTemplate + Meta 策略 spec + 当前 state 合成本次的 rubric 集合。 载体：brain/rubrics/<domain>/*.yaml + brain_harness/rubric_composer.py。

能力 ③ Task Decomposition Policy

把高级问题拆成 L10 的原子任务序列。Policy 不是硬编码——它从 Meta 策略 spec 的 atomic_task_decomposition 字段读取。 Brain 只负责选哪条策略、按依赖图编排。 载体：brain_harness/task_decomposer.py。

能力 ④ Hand Skill Registry + Recommender

每个原子任务该用哪个 base_hand_id（数据型轻 LLM / 推理型中等 / 综合型工具循环 / 闭源 / 开源）由 Recommender 决定。 输入：原子任务的 recommended_skill_class + 当前 capability inventory + budget。 载体：brain/hand_skills/registry.yaml + brain_harness/skill_recommender.py。 用例：macro_rates 任务在预算紧时挑 haiku，预算松时挑 sonnet。

能力 ⑤ State Disclosure Policy（关键！）

Hand 不应看到全部 state。Brain 根据原子任务的 state_slice_template，决定暴露哪一片给这个 hand。 例：macro_rates 只看到 FRED 相关连接器和宏观规则，看不到行业数据；sector_rotation 反之。 载体：brain_harness/disclosure.py，与既有 loom/resource_disclosure.py 合并。 这是把"Brain 的策略"和"Hand 的执行"真正分开的物理隔离。

能力 ⑥ Acceptance & Repair Policy

Review 阶段的判定规则：什么样的 quality_gap 触发修复，最多修几次。Policy 也由 GoalTemplate 与 Meta 策略共同决定（不同策略容忍度不同）。 载体：brain_harness/acceptance_policy.py。

能力 ⑦ Strategy Distillation（写回）

成功的 episode → 蒸馏出新的 Meta 策略 spec 或更新已有策略。 失败的 episode → 在策略 spec 上 confidence 降级或 supersedes 标记替换。 载体：扩展既有 loom/brain_harness/distiller.py。 这条回路完成 L8 中"反馈 → 长期 state"的最大循环。

Level 13 · NanoRLM 对照

把 NanoRLM 的 rollout/RL 训练范式映射到 Loom 的 harness

NanoRLM 是什么：一个最小可读的 agentic RL playground——单环境（MathEnv）、多轮自我修正、GRPO 组内相对优势、on-policy 更新模型权重。 它把"rollout 数据采集"和"权重更新"压缩到一个可读的代码库里（nanorllm/{agents,rollout,core,algos,rewards,trainer}）。

13.2 — Loom 应该借鉴的 7 件事

① 数据层分层：Trajectory（语义）/ RolloutView（token）/ Rollout（合一）

NanoRLM 把同一次执行切成三层： Trajectory（observation→action→feedback 语义流，给人看 / 用于评估）、 StepRolloutView（prompt_ids + response_ids + response_logprobs，给训练器用）、 Rollout（绑定两者 + metadata）。 这三层在 Loom 现在的 WorkflowEpisode 里没有清晰拆开——目前 phase 事件混杂了语义和原始 payload。

落到 Loom： brain/episodes/<id>.jsonl 之外，再开一个 brain/rollouts/<id>.jsonl 专门存 token 级数据； adapter 的 capabilities.supports_logprobs 决定是否落盘。 关闭 logprobs 时 RolloutView 退化为 input/output 文本对，仍可用于 SFT-style 数据。

② Multi-sample dispatch（best-of-N / 自一致性）

NanoRLM 的 execute_tasks(num_samples_per_task=N) 对同一个 task 跑 N 次，因为 GRPO 需要组内方差。 即使 Loom 不训练模型，这件事也有三个直接收益：

  • 分歧度即置信度——N 次结果一致 → high confidence；分裂 → low confidence。直接喂进 L3 的 trust_aggregate。
  • Best-of-N 选优——按 rubric 评分挑最好一个返回，剩余存档供 replay。
  • 未来 RL 准备——当 Loom 切到开源 adapter 时，这批数据天然就是 GRPO 训练集。

落到 Loom：在 hand spec 加 samples_per_dispatch: int = 1； BrainOrchestrator 拿到 N 份 artifact 后调 SampleAggregator 决定返回策略 （best-of-rubric / majority-vote / all）。

③ Group-relative scoring（即使不训练也能用）

GRPO 的核心数学是：advantage = (reward - group_mean) / (group_std + eps)。 Loom 即使没有 backprop，也能复用这个归一化逻辑给 每次 dispatch 的 hand artifact 打"相对分"：

  • 同一个原子任务（L10 的 atomic_task_id，例如 market.macro_rates）在历史 episode 里跑过 K 次。
  • 给新 artifact 算 rubric 得分，与历史均值/方差对比，得到一个"相对优于历史"的分数。
  • 这个分数直接进 L3 的 trust_aggregate，作为"这次 macro_rates 比平时好/差"的calibrated 信号。

落到 Loom：新建 brain_harness/relative_scorer.py，维护 brain/scoring_history/<atomic_task_id>.jsonl（reward 时间序列）； has_relative_signal() 用来短路掉历史方差为 0 的情况（避免假信号）。

④ Reward Synthesizer（把 L8 的反馈信号合成标量）

NanoRLM 有干净的 RewardOutput {reward, metadata, is_correct}。Loom 没有 env 反馈，但有 L8 列的五类信号 （接受/拒绝/编辑/撤回/明确反馈）。把它们合成标量 reward 才能让上面 ③ 跑起来。

L8 信号合成贡献
用户 lock+1.0
用户 edit+0.3（部分接受）
用户 reject / 撤回0.0
跨 hand 验证：被另一 hand 否证−0.5
rubric 覆盖率×coverage
明确文字反馈（LLM-as-judge 解析）±0.5
时间衰减：市场后验对错滞后 +0.5/−0.5，按 watch_conditions 触发

落到 Loom：新建 brain_harness/reward_synthesizer.py，订阅 L8 那 5 类事件， 生成 RewardRecord {episode_id, hand_id, atomic_task_id, reward, components, ts}， 落 brain/rewards/<hand_id>.jsonl。

⑤ 结构化 Termination Reason

NanoRLM 在 trajectory 上明确标 termination_reason（done / max_steps / error）。 Loom 现在的 phase_trace 没有 enum 化的终止理由。

落到 Loom：在 WorkflowEpisode 的最终状态加 termination_reason: Literal["synthesis_success", "budget_exceeded", "repair_budget_exceeded", "user_interrupt", "adapter_error", "gap_unresolved", "schema_violation_unrecoverable"]。 Replay 工具按 reason 分组统计——比例失衡（例如 30% 都是 repair_budget_exceeded）就是"该原子任务的 rubric 设计有问题"的信号。

⑥ Task 维度的可批处理样本仓库（dataset curation）

NanoRLM 的 execute_tasks 把 (task, sample, rollout) 串成三元组，方便后续切批训练。 Loom 目前 episode 之间相互独立，没法做"把过去 100 次 market.macro_rates 的结果拉出来回看"。

落到 Loom：给每条 hand artifact 打 atomic_task_id + strategy_id（L10/L11 的 id）两个索引键， 再加一个 query layer brain_harness/artifact_lake.py，支持： find(atomic_task_id, strategy_id, since, reward_above)。 这就是"未来 SFT/DPO 数据集" 与"今天的 best-practice 提取池"二合一。

⑦ 浏览器 trajectory viewer = 已有的 detail overlay

NanoRLM 自带一个 HTML viewer + JSON 导出。Loom 现成的 bridge/webview/loom-detail-overlay.js + L0/L1/L2 密度切换其实就是同一个东西，但目前 overlay 只盯 hand artifact 自身， 不能 replay 一整条 episode 的事件流。

落到 Loom：给 overlay 加一个 "Episode timeline" tab，读 brain/episodes/<id>.jsonl 渲染成时间轴； 点任一事件可下钻到对应 artifact / prompt / patch。

13.3 — Loom 多出 NanoRLM 没有的东西（说明边界）

不要被借鉴清单带偏——以下是 Loom 该 own 的、NanoRLM 不涉及的：

  • 多 Hand 编排：Brain → N 个 Hand 并行 / 串行 + 跨 Hand 验证。NanoRLM 是单 agent。
  • 13 维 State 模型（L3）：NanoRLM 只有 message history。Loom 是 state-first，13 维各司其职。
  • 跨 episode 记忆：BrainState / IntentWiki / GoalContext / Flywheel。NanoRLM 每 episode 重置。
  • 异构 adapter：闭源 / SDK / 开源 三类统一契约。NanoRLM 只有 HF causal LM。
  • Meta 策略（L11）：从用户行为蒸馏 strategy spec。NanoRLM 完全没有这层。
  • 原子任务库（L10）：Brain 自带 rubric / acceptance / schema。NanoRLM 的任务由 dataset 直接给。
  • 面向人的数据产品：data_product.v1 + L0/L1/L2 渲染层。NanoRLM 没有 UI 层。

13.4 — 借鉴落到实施清单的改动

原 12 步实施顺序里，要追加 4 件 NanoRLM 衍生事项：

  1. RolloutView 层：新建 brain/rollouts/<id>.jsonl 与 workflow_rollout.v1.json schema； adapter 按 supports_logprobs 决定写 token 级还是文本级。
  2. Multi-sample dispatch：hand spec 加 samples_per_dispatch， 新建 brain_harness/sample_aggregator.py。
  3. Reward Synthesizer + Relative Scorer： brain_harness/reward_synthesizer.py + brain_harness/relative_scorer.py；落 brain/rewards/ 与 brain/scoring_history/。
  4. Artifact Lake + Termination Reasons： brain_harness/artifact_lake.py 提供按 atomic_task_id/strategy_id 检索； 给 WorkflowEpisode 添加 enum termination_reason。
哲学差异（一句话总结）： NanoRLM 把一个简单环境压扁到训练循环里，Loom 把复杂业务编排开成 state-first pipeline—— 两边都靠"把任务原子化、把数据分层、把信号显式化"才能跑通。 Loom 借鉴 NanoRLM 的不是"做 RL"，而是"把每次执行变成可分组、可比较、可回放的样本"。
注意：不要把 NanoRLM 的"on-policy 更新模型权重"硬塞进 Loom——只要 Hand 是闭源 API，这条路就是死的。 但所有为 RL 准备的数据结构（RolloutView / RewardRecord / Termination Reason / Relative Scorer）即使不训练也立刻有用。

验收 · 怎么算"做对了"

八条验收标准

  • 1 · 一次 LoomCoreAgent.analyze(question) 调用产出可被事件日志离线 replay 还原的 WorkflowEpisode。
  • 2 · 同一个 orchestrator 跑通 闭源 / SDK / 开源 三种 adapter，不用改 LoomCoreAgent。
  • 3 · 违反 schema 的 hand artifact 被校验闸拦截，触发带反馈的修复 dispatch，不是默默通过或 raw retry。
  • 4 · 未过晋升门的 runtime hand 不能写入 brain/hand_specs/。
  • 5 · GET /brain/runs/{id} 返回的 JSON 通过 brain.data_product.v1 schema 校验。
  • 6 · 既有 /analyze、presentation overlay、hand artifact UI 不回退。
  • 7 · （来自 L13）hand spec 设 samples_per_dispatch=3 时，单次 episode 落 3 份 artifact 到 brain/rollouts/<id>.jsonl，并按 best-of-rubric 返回最佳 1 份；其余可在 overlay 中查阅。
  • 8 · （来自 L13）同一原子任务跑过 ≥5 次后，relative_scorer 能为新 artifact 算出归一化分数， 并体现在 trust_aggregate 上；termination_reason enum 在 episode 终态必填。
风险护栏：持久 Hand 创建必须 domain 主权 + eval + 用户未否决 + 预算内 四项联合通过。任何 prompt 不能绕过晋升门直接落盘。
