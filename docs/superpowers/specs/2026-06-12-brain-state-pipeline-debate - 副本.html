1

Problem · 当前方案的缺口

从既有代码出发，对照源 spec，识别 10 个结构性问题：

P1 · "State-first" 声明但 state 清单不完整

spec 列出 episode_id / goal / rubrics / hand_specs / phase_trace / rubric_coverage / quality_gaps / data_product。任何真实编排器还需要： 能力状态（每个 adapter 能做什么）、预算/配额状态（token、成本、时延、墙钟）、 上下文窗口状态（注入了什么、裁剪了什么）、信任/出处状态（每条 claim/hand 的置信与互证）、 记忆状态（情境/语义/程序三类）、用户意图漂移状态、 分支/探索状态、失败/修复状态（不止 quality_gaps）、 外部世界状态（时钟、连接器健康、数据新鲜度）、中断状态（用户编辑、取消）。

P2 · 流水线被画成线性 1→8，但真实流是事件驱动

Plan 会反复迭代，Hand 可能与 Brain 协商，用户可能中断，外部源可能失效。这些都是循环而非步骤。把线性 8 步当成主结构， 实际上把方案试图摆脱的"固定 fanout"刚性，又以更粗的粒度引了回来。

P3 · Hand 选择仍耦合 domain

"state-first" 的承诺在 dispatcher.resolve(domain) 还在工作时就被打破了。要真正以 state 驱动，规划器必须把 完整的 workflow 状态（goal + rubric + capability inventory + budget）当输入，而不是查"domain → hands"表。

P4 · 既有 Adapter 抽象层在 spec 里隐身

仓库里已经有六种 provider，spec 却没说"hand spec 在 dispatch 时绑定到哪个 adapter"。 没有这层映射，每个阅读者都会重新发明一套，无法落地通用方案。

P5 · "Persistent hand spec" 没有定义

无 schema、无版本、无所有者、无能力契约、无晋升门槛。spec 第 8 节关于"受控持久化"的边界是策略，但缺机制。

P6 · data_product.v1 只命名未定义

Headless API 依赖一个版本化的数据产品，但版本号、字段 schema、迁移路径都没有给。

P7 · 三类 agent 的 harness 完全没被讨论

这是用户明确点名的问题。Spec 假定 LLM 就是 provider_client.get_client_for_brain()，未推演不同 provider 类别下 harness 能/不能控制什么。

P8 · 没有持久化与崩溃恢复设计

Phase 半路失败能不能续？hand artifact 是否先落盘再 synthesize？phase_trace 是边走边写还是事后写？均未交代。

P9 · 没有并发 episode 契约

GoalContext 是共享对象。两个并行 episode 写同一 goal 的 synthesis_history 会冲突。spec 只说"写入 GoalContext / Flywheel"， 未说明顺序、锁、合并。

P10 · Repair Loop 无终止规则

follow_up 可以触发，但最大重试次数、最大成本、最大时延都没设。对抗性输入下会无限修复。

2

Ideal · State-First Pipeline 应承载的 state 维度

将 WorkflowEpisode 提升为一等对象。一次任务运行 = 一个有类型、可持久、可查询、可重放的记录。它承载下面 13 类 state：

2.1

目标与意图 Goal & Intent

goal_id / goal_type / title / success_criteria / deadline / priority / owner_intent（链到 IntentWiki）/ acceptance_policy（strict | best_effort | exploratory）。

2.2

规划与评分维度 Plan & Rubric

rubrics[]: {dimension, requirements, acceptance, source: brain|template|user_pin}； excluded_dimensions / excluded_hands / priority_signal / regime_relevance。

2.3

能力清单 Capability Inventory

规划时刻快照：available_adapters[] 每个含 adapter_id, model_class, modalities, tool_whitelist, max_context, p50_latency_ms, cost_per_call, trust_tier；available_hands[] 含状态 ready/degraded/unavailable。

2.4

Hand Spec 实例

每次 dispatch：{hand_id, base_hand_id, lifecycle: runtime|persistent, adapter_binding: adapter_id, task, capabilities, rubrics, acceptance, input_budget, output_schema}。 adapter_binding 把"hand spec"与既有 provider registry 显式连起来——这是原 spec 的关键缺漏。

2.5

执行轨迹 Execution Trace

事件溯源、仅追加：phase.start / phase.end / dispatch.sent / dispatch.token_delta / dispatch.tool_call / dispatch.artifact / dispatch.error / review.flag / repair.requested / synthesis.partial / user.interrupt / user.accept / state.checkpoint。phase_trace 与 rubric_coverage 是这条日志的派生视图。

2.6

预算与配额 Budget

{token_total, token_used, cost_cap_usd, cost_used_usd, wall_clock_ms, deadline_ts}； 再细分 per_dispatch_budget / per_phase_budget，防止单 hand 耗尽 episode。

2.7

上下文与记忆 Context & Memory

context_packet[]：每次 agent 调用注入的 rule_ids/framework_ids/notes/intent_tail/last_synthesis_hash； pruned[]：预算压力下被丢弃的内容（可按需召回）； 记忆引用：episodic / semantic / procedural 三类。

2.8

证据信任与出处 Evidence / Trust / Provenance

从 hand artifact 汇集的 evidence[]：{claim, support, source, source_tier, freshness, confidence, hand_id, rubric}；trust_aggregate：每个 rubric 的互证计数与冲突；继承 GoalContext.contradiction_log。

2.9

质量缺口与修复 Quality Gaps

quality_gaps[]: {dimension, kind: missing|stale|low_confidence|contradicted, severity, recommended_action}； repair_history[] + repair_budget_remaining。

2.10

世界快照 World State

{ts, market_clock_state, connector_health: {id: ok|degraded|stale}, data_freshness: {source: ts}}， 规划时刻冻结，保证 replay 可复现。

2.11

分支与探索 Branch / Exploration

branch_id / parent_branch / siblings[]，用于 what-if 与 framework A/B。v1 不必启用，但预留字段避免后期破坏性变更。

2.12

用户介入 User Interaction

user_interventions[]：编辑、锁定、拒绝、纠正（喂给 CorrectionDetector）； pending_decisions[]：Brain 显式向用户求决的位置。

2.13

输出 Output

synthesis（stance / confidence / drivers / reversal / watch_conditions）+ data_product（带 schema URL 的版本化负载） + presentation_hint（L0–L3 分层，复用已有 _card_detail_schema）。

设计约束：所有维度必须 (a) 强类型，(b) 可 JSON 序列化，(c) 可被 UI 通过 anchor id 引用，(d) 可从事件日志中重放。

3

Gap · 闭源 / SDK / 开源 三类 agent 的 Harness 差异

✓ 关键洞察：Harness 拥有状态，agent 只是被调用的纯函数。三类 agent 的差异只在控制点数量上—— 所以通用方案的核心是：同一份 Adapter 协议，可选能力位用于按 provider 启用增强行为。

3.1 通用不变面（任何 harness 都必须实现）

  • Adapter 契约：async def invoke(envelope) -> AsyncIterator[event]——这与 loom_core/agent_adapters/providers/sdk_legacy.py::InProcessAdapter.invoke 已实现的形状一致，沿用即可。
  • 信封序列化：把 WorkflowEpisode 的切片注入 prompt / 工具定义 / system message。
  • 事件归一化：所有 adapter 对外只发统一事件 run.started / run.tool_call / run.artifact / run.partial / run.error / run.completed。
  • 输出 schema 校验：命中状态之前必须先过 jsonschema。
  • 预算治理：BudgetGovernor 监听事件流，超阈值即提前终止。
  • 审计日志：所有信封 + 所有事件均落盘，用于 replay 与回归测试。

3.2 闭源 API Claude / GPT / Gemini

可控：请求/响应消息、system prompt、tool 定义、流式 token。不可控：内部草稿区、模型权重、确定性 seed、中途状态注入（除工具调用结果外）。

  • 所有 state 必须序列化到输入里 —— system prompt 承载稳定角色契约，messages 承载本次 episode 上下文，tool 定义承载能力面。
  • 中途介入只能靠工具拦截 —— harness 实现每个工具，因此能 (a) 在工具返回时注入额外 state，(b) 拒绝调用，(c) 提前结束循环。
  • Replay = "input + provider + model_id" 日志，不是 bit-deterministic，但够用于调试。
  • 校验必须防御性写 —— 闭源模型会幻觉字段，所有 artifact 过 jsonschema，失败则触发"带 diff 反馈"的修复 dispatch，不要 raw retry。
  • 成本 / rate-limit 治理只能在 harness 一侧；模型内部没有预算。
  • 记忆 = 外部存储 + RAG 注入。

3.3 SDK 工具循环 Anthropic SDK / OpenAI SDK

定位：闭源 API 的严格超集，多了更细的事件流。

  • 结构化工具循环 —— 工具调用更易拦截，harness 拥有循环主权。
  • 流式事件 —— partial 输出转 run.partial，前端可实时渲染（与既有 partial_render 路径打通）。
  • 内置重试 / 退避 —— 仍要用同一 BudgetGovernor 包一层，SDK 自动重试会让成本失控。
  • 没有新增控制点；要更多控制就得切到开源自托管。

3.4 开源 / 自托管 vLLM / llama.cpp / Ollama / 自建推理服

新增控制面：

  • 确定性 seed —— 同输入 + 同 seed → 同输出，支持 bit-exact replay。
  • Token 级流式 + logprobs —— 用于校准与置信度建模。
  • 生成中导向 —— guidance / 约束解码在解码器层强制 JSON Schema，而不是事后校验。
  • 采样器、推测解码、KV cache 复用 —— 性能杠杆。
  • 同一 adapter 后挂多模型 —— 小快模型路由 + 大模型综合的回退链。
  • 信任折扣 —— 小开源模型可能漏细节，rubric 覆盖度门槛要更严、repair 预算要更高。

通用契约的应对：Adapter 暴露可选能力位 supports_seed / supports_logprobs / supports_constrained_decoding / supports_tool_call_loop。orchestrator 查询能力位、按可用项启用增强； 不可用时优雅降级（replay 从"deterministic"退到"input-equal"）。质量门槛在所有 provider 上一视同仁，不打折扣。

3.5 通用 Harness 的 Adapter 家族矩阵

Adapter 家族仓库中已有 / 待新增能力位
HTTP API（闭源） providers/cc.py，待补 openai_api.py / gemini_api.py supports_tool_call_loop, supports_streaming
SDK 工具循环 providers/sdk_legacy.py::InProcessAdapter，待补 anthropic_sdk.py + supports_partial_events
开源 / 自托管 待补 vllm.py / llama_cpp.py / ollama.py + supports_seed, supports_logprobs, supports_constrained_decoding
进程子代理（已有） codex / herms / opencode / openclaw 能力位由各自配置声明

关键结论：新增 adapter 家族时 orchestrator 不需要改动，因为它只面向归一化事件流和 capability 字典编程。

Strategy · 落地策略与实施顺序

4.1 升级后的 state-driven pipeline（替代原来的线性 8 步）

Planning构造 episode、生成 rubric、快照 capability inventory、计算 budget。
DispatchingHandPlanner 基于完整 episode state 输出 hand spec + adapter_binding，并行/串行调度。
Reviewing事件流过 BudgetGovernor、jsonschema 校验、rubric 覆盖度评估，产出 quality_gaps。
Repairing带反馈 diff 的二次 dispatch；受 repair_budget_remaining + max_iter 双重终止。
Synthesizing融合 hand artifacts + GoalContext + IntentWiki，输出 stance/confidence/reversal/watch。
Persisting校验 data_product.v1 → 写 episode jsonl → 更新 GoalContext / Flywheel / intent_stream。
Interrupted用户在任何时点 lock/edit/cancel，事件入日志，orchestrator 转此状态。
Failed预算耗尽或不可恢复错误；最近 state.checkpoint 决定重启策略。

这是状态机而非线性：每个状态有自己的进入/退出转移，所有转移产生事件。phase_trace、rubric_coverage 都是事件日志的派生视图。

4.2 通用 Harness 的 Adapter 协议（最终形态）

class AgentAdapter(Protocol):
  id: str
  capabilities: dict ＃ supports_seed / supports_logprobs / supports_tool_call_loop ...
  async def invoke(envelope: Envelope) -> AsyncIterator[RunEvent]: ...
  async def cancel(run_id: str) -> None: ...

＃ 归一化事件类型
RunEvent = run.started | run.partial | run.tool_call | run.token_delta
         | run.artifact | run.error | run.completed

4.3 Hand 选择改为 state-aware

把 dispatcher.resolve(question, context) 替换为 HandPlanner.plan(episode_state)：

  • 输入：完整 episode 快照（goal + rubrics + capability inventory + budget + 历史 GoalContext）。
  • 输出：hand_specs[]，每个含明确的 adapter_binding。
  • domain 仅作为输入提示，不作为决策表。

4.4 持久 Hand Spec 的 schema 与晋升门

路径：brain/hand_specs/<domain>/<hand_id>.json。必备字段：

{
  "hand_id", "base_hand_id", "version",
  "owner_domain", "task_template", "capabilities",
  "rubrics_default", "acceptance_default",
  "created_from_episode", "created_at",
  "last_eval_ts", "eval_score", "deprecation_status"
}

晋升门规则：runtime → persistent 必须满足 (a) domain 主权认领、(b) 持出测试集 eval 达标、(c) user_interventions 未否决该 artifact、(d) 成本与时延在预算内。

4.5 brain.data_product.v1 显式 schema

放在 brain/schemas/brain.data_product.v1.json。字段：version / episode_id / goal_id / synthesis / evidence[] / quality_gaps[] / watch_conditions[] / regime_relevance / produced_at / expires_at。Headless API 必须先过 schema 才能返回。UI 渲染变成纯函数。

4.6 Budget Governor + 校验闸 包住每次 dispatch

  • 校验：每个 run.artifact 都过 jsonschema。失败 → 修复 dispatch 携带 schema 违规反馈，不是 raw retry。
  • 预算：监听 run.token_delta / run.completed，触线即抛 BudgetExceeded，orchestrator 提前转入 Synthesizing 并把缺口写入 quality_gaps。

4.7 Replay / 审计

读 brain/episodes/<episode_id>.jsonl，把事件流喂回同一个 orchestrator，但不调真实 adapter。用途：调试、回归、微调数据、eval 评测。开源 adapter 额外存 seed → 可 bit-exact 重跑；这条 replay 通路在闭源 / SDK 上仍可工作（仅退化到"input-equal"）。

4.8 Headless /brain/runs 路由

  • 挂在既有 Brain FastAPI 服务（loom/brain.py，port 3002）。
  • POST /brain/runs 立即返回 episode_id；实际事件流写入 brain/episodes/<id>.jsonl，并通过 patch_webview / WS 推送。
  • GET /brain/runs/{episode_id} 返回 schema 校验过的 data_product + workflow_state 摘要视图。
  • /analyze 变成"建 episode → 同步跑 → 加 presentation 返回"的薄壳，与 headless 路径共享同一 LoomCoreAgent。

4.9 并发与持久

  • 同一 goal_id 写 GoalContext.synthesis_history / contradiction_log 时取一把写锁；不同 goal 自由并发。
  • Episode 日志仅追加；最近的 state.checkpoint 是恢复点。
  • 崩溃后：orchestrator 扫描 brain/episodes/，对最后事件不是 Persisted / Failed 的 episode 走恢复或标 Failed。

4.10 实施顺序（建议分相）

  1. 定义 WorkflowEpisode dataclass + JSON schema，附加式串进 LoomCoreAgent.analyze()，不改既有行为。
  2. 增加事件日志 writer（brain/episodes/<id>.jsonl），把 phase_trace / rubric_coverage 改为派生视图。
  3. 给所有现有 adapter（cc / codex / herms / opencode / openclaw / sdk_legacy）填 capabilities 字典。
  4. 引入 BudgetGovernor 与 schema 校验闸，包住每次 dispatch。
  5. 把 dispatcher.resolve() 替换成 HandPlanner.plan(episode_state)，domain 降为输入提示。
  6. 落地 brain.data_product.v1.json 与 /brain/runs。
  7. 定义 persistent_hand_spec schema 与晋升门，新建 brain/hand_specs/ 存储。
  8. 至少新增一个开源 adapter（如 vllm.py），把通用契约跑通。

5 · 验收标准

  • 一次 LoomCoreAgent.analyze(question) 产出可被事件日志离线 replay 还原的 WorkflowEpisode。
  • 同一 orchestrator 跑通 闭源 / SDK / 开源 三种 adapter，无需改 LoomCoreAgent。
  • 违反 schema 的 hand artifact 被校验闸拦截，触发修复 dispatch，而非默默通过。
  • 未过晋升门的 runtime hand 不能写入 brain/hand_specs/。
  • GET /brain/runs/{id} 返回 schema 合规的 brain.data_product.v1 JSON。
  • 既有 /analyze、presentation overlay、hand artifact UI 不回退。

7 · 关键边界 / 风险护栏

不可越界：持久 hand 创建必须受 (a) domain 主权 + (b) eval 通过 + (c) 用户未否决 + (d) 预算内 四项联合约束。 任何 prompt 不能绕过晋升门直接落 brain/hand_specs/。
降级是合规结果：预算耗尽 / 校验反复失败 / 用户中断，都应被记成事件并写入 quality_gaps， 而不是当成隐式失败被 swallow。
通用性的核心保证：orchestrator 只面向 AgentAdapter 协议 + 归一化事件流 + capability 字典编程。 新增任何 adapter 家族（闭源、SDK、开源、子代理进程）都不需要触碰 LoomCoreAgent。

8 · 留给用户决策的开放问题

  1. WorkflowEpisode 存储用 JSONL 文件（与 intent_stream.jsonl 对齐，崩溃恢复简单）还是 SQLite 表（可查询历史）？
