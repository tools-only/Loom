Rewarded Intent Harness Architecture

将 BrainHarness 从“读取记忆并拼接 prompt”的浅层机制，升级为可维护意图状态、选择策略、评估输出、分配奖励并持续更新的通用学习型 harness。

Date: 2026-06-09 Scope: Generic Brain Harness Current Domain: Investment Research Pattern: Contextual Bandit + Reward Ledger

1. 背景与问题

当前 intent layer 已经能捕获用户行为、提炼长期意图，并在生成时激活部分意图。但它本质上仍是 memory layer： 行为被写成文件，意图被表达为文字，生成时主要依赖 prompt 注入。这不足以支撑高级 BrainHarness。

关键缺陷：Brain 没有显式维护“策略选择、奖励信号、评估器、归因更新”。因此它不能真正学习哪类意图在什么上下文中应该被采用，也无法解释一次生成为什么好或差。

2. 目标架构

新架构称为 Rewarded Intent Harness。它不直接追求完整强化学习，而是采用更适合产品环境的 RL-lite： 每次生成是一个 episode，Brain 根据当前状态选择 intent policies，生成后由 evaluator ensemble 打分，再把 reward 归因回 intent、policy、hand choice 和 prompt constraint。

1 Intent Events

用户行为、资源分享、anchor 操作、反馈、编辑。

2 Intent State Builder

将事件转为长期意图状态、belief、activation prior。

3 Policy Planner

选择本次生成应采用的 intent policies。

4 Generation

编排 hands、工具、检索、输出结构。

5 Evaluator Ensemble

评估意图覆盖、相关性、时效性、决策价值。

6 Reward Ledger

记录每个 episode 的奖励和诊断。

7 Credit Assignment

判断奖励应归因给 intent、policy、hand 或 prompt。

8 Policy Update

更新权重、失败模式、激活先验和策略钩子。

3. 核心对象模型

IntentState

长期用户意图的结构化状态，不只是文字描述。

可执行策略，而不是 prompt 片段。

    }
  ]
}

4. 为什么用 Contextual Bandit，而不是完整 RL

当前系统主要使用闭源 API，因此不能把这个 harness 设计成 PPO、GRPO 或 DPO 那类直接更新模型参数的传统 RL。 更准确的定位是 Closed-Model RL-lite 或 Agentic Policy Learning Harness： 不训练 LLM 本体，而是训练 Brain 外部的策略层。

方案 优点 问题 建议
Prompt + Memory 实现快，容易调试 没有奖励和归因，无法学习策略质量 保留为输入层，不作为核心 harness
Contextual Bandit 每次生成都是一次可评估 episode，适合产品交互 不处理复杂多步长期回报 第一阶段推荐
Full RL 理论上可优化长期策略 需要大量 episode、稳定环境和明确 reward 暂不直接上，后续可演进
结论：闭源 LLM 负责推理与生成，BrainHarness 负责可训练的外部策略。可被学习和更新的是 workflow policy、retrieval policy、intent activation policy、prompt constraint policy、critic/debate policy、output structure policy 和 hand selection policy。

5. 闭源 API 下的 Agentic RL 边界

一般意义上的 agentic RL 往往默认存在一个可训练模型：模型 rollout，reward model 打分，然后通过 PPO、DPO、GRPO 等方法更新模型权重。 但在闭源 API 场景中，模型权重不可更新。因此，harness 不应声称自己在训练 LLM，而应明确训练的是 agent 外部控制策略。

不训练的部分
  • LLM weights
  • Decoder policy
  • Base reward model weights
  • API provider 内部模型行为
可以训练/更新的部分
  • Workflow policy：调用哪些 hand / tool / agent
  • Retrieval policy：何时检索、检索什么、检索多少
  • Intent activation policy：哪些长期意图参与本次生成
  • Prompt constraint policy：采用哪些结构和约束
  • Critic/debate policy：是否启用 critic、自辩或多候选
  • Output structure policy：用 brief、memo、matrix 还是 graph
  • Hand selection policy：不同 hand 在不同状态下的历史收益

推荐闭环

Closed API LLM = reasoning / generation engine
BrainHarness = trainable policy layer
Episode Ledger = offline dataset
Evaluator Ensemble = reward source
Credit Assignment = update mechanism

为什么这仍然有价值

即使不更新模型权重，Brain 仍然可以学习“如何使用模型”。这包括什么时候调用资源检索、什么时候启用 critic、什么时候添加风险矩阵、什么时候优先调用某个 hand，以及哪些长期 intent 在什么任务中应该激活。 这些策略选择会直接影响最终输出质量，且可以被 episode reward 持续更新。

未来开源模型路径

当前积累的 episode ledger 不会浪费。未来如果接入开源 planner model 或 domain model，可以将这些 episode、reward report、credit assignment 转化为 preference dataset，用于训练 judge model、reward model，或通过 DPO/GRPO 微调 planner。

6. Brain-Hand 分离架构下的 Harness 作用面

Loom Core 的关键边界是：Brain 不直接实现具体领域业务，Hand / external agent 执行领域分析；Brain 负责将用户意图包装成任务 envelope，选择 hand，接收 artifact，编排结果，并记录 harness signals。 Rewarded Intent Harness 应该作用在这条边界上，而不是把 hand 的领域职责上移到 Brain。

1 Task State

用户问题、anchor context、intent graph、资源状态、历史 reward。

2 Workflow Policy

决定调用哪些 hand、是否 fanout、是否串行/并行/二阶段。

3 Hand Envelope Shaping

为每个 hand 注入不同任务、约束、资源菜单和 intent hooks。

4 Hand Execution

hand 返回 artifact、claims、confidence、resources、gaps。

5 Artifact Critic

评估每个 hand 是否满足任务、证据是否足够、是否跑偏。

6 Synthesis Policy

决定如何加权、冲突解决、引用哪些 hand 结果。

7 Reward & Credit

把最终 reward 归因回 workflow、hand、resource 和 synthesis。

8 Policy Update

更新 hand selection、routing、prompt constraints 和 evaluator 权重。

6.1 BrainHarness 如何影响 hand 架构编排

编排层 BrainHarness 决策 对 Hand 的影响 Reward 来源
Hand selection 根据 intent、domain、历史 hand reward 选择 hand 集合。 不是固定 market/sentiment/target/position，而是按任务状态选择。 hand artifact usefulness、最终 synthesis 引用率、用户后续行为。
Execution topology 决定 full fanout、single hand、sequential hand、critic round 或二阶段检索。 hand 可以并行跑，也可以让一个 hand 的 artifact 成为另一个 hand 的输入。 质量提升是否抵消 latency / token 成本。
Envelope shaping 为不同 hand 生成不同任务描述、资源菜单、intent constraints。 同一个用户问题到不同 hand 时不是同一 prompt，而是 role-specific task。 hand 是否返回更具体 key_claims、是否减少 gaps。
Resource allocation 决定哪些 hand 能访问哪些资源、是否要求 fresh context。 market hand 可能拿新闻，position hand 可能拿用户仓位，target hand 可能拿估值框架。 freshness、evidence grounding、无关资源污染程度。
Budget control 根据预期收益控制 hand 数量、critic 次数、上下文长度。 高价值任务启用更深编排，低价值任务走轻量路径。 reward / latency / cost 的综合收益。

6.2 BrainHarness 如何影响 hand 结果编排

Hand artifact 不应该只是被拼接到 Brain synthesis prompt。Rewarded Harness 应在 artifact 进入 synthesis 前做结构化处理：

Artifact Normalization

把每个 hand 输出规整为 claims、evidence、confidence、gaps、intent coverage、resource usage。

Claim Graph

将不同 hand 的 key_claims 变成支持、冲突、补充、缺证据的 claim graph。

Hand Weighting

根据 hand 历史 reward、当前任务匹配度、artifact confidence 动态加权。

Conflict Resolution

当 market 和 sentiment、target 和 position 结论冲突时，要求 Brain 显式解释冲突来源。

Intent Coverage Gate

检查 active intents 是否在 hand artifacts 中已有支撑；不足时触发补充 hand 或标注 gap。

Synthesis Contract

Brain synthesis 必须说明采用了哪些 hand claim，忽略了哪些 claim，以及原因。

7. Evaluator Ensemble

生成完成后自动运行多评估器，避免只依赖用户显式反馈。

IntentCoverageEvaluator

检查激活 intent 是否被实际满足。

RelevanceEvaluator

检查是否强行塞入无关长期偏好。

FreshnessEvaluator

需要时效信息时，检查是否检索并使用近期上下文。

DecisionUsefulnessEvaluator

判断输出是否提高决策质量，而非只增加内容。

UserStyleEvaluator

检查粒度、表达和结构是否符合用户偏好。

DomainEvaluator

由 domain pack 提供，例如投资研究、写作、代码审查。

11. 架构原则

  • 核心 harness 必须通用，投资研究只是 domain pack。
  • 事件流是证据，不是长期意图本身。
  • 长期意图必须有 belief、reward history、failure modes 和 activation policy。
  • 生成时必须显式记录采用了哪些 intent 和 policy。
  • 生成后必须评估，而不是假设 prompt 注入就代表满足意图。
  • 奖励更新必须可解释，避免隐藏式用户画像。
  • Brain 负责策略、编排、评估和归因；Hand 负责领域执行和 artifact 生产。
  • Harness 应影响 hand selection、envelope shaping、artifact weighting，而不是吞并 hand 的领域职责。
