Rewarded Intent Harness Architecture

将 BrainHarness 从“读取记忆并拼接 prompt”的浅层机制，升级为可维护意图状态、选择策略、评估输出、分配奖励并持续更新的通用学习型 harness。

Date: 2026-06-09 Scope: Generic Brain Harness Current Domain: Investment Research Pattern: Contextual Bandit + Reward Ledger

1. 背景与问题

当前 intent layer 已经能捕获用户行为、提炼长期意图，并在生成时激活部分意图。但它本质上仍是 memory layer： 行为被写成文件，意图被表达为文字，生成时主要依赖 prompt 注入。这不足以支撑高级 BrainHarness。

关键缺陷：Brain 没有显式维护“策略选择、奖励信号、评估器、归因更新”。因此它不能真正学习哪类意图在什么上下文中应该被采用，也无法解释一次生成为什么好或差。

2. 目标架构

新架构称为 Rewarded Intent Harness。它不直接追求完整强化学习，而是采用更适合产品环境的 RL-lite： 每次生成是一个 episode，Brain 根据当前状态选择 intent policies，生成后由 evaluator ensemble 打分，再把 reward 归因回 intent、policy、hand choice 和 prompt constraint。

1 Intent Events

用户行为、资源分享、anchor 操作、反馈、编辑。

2 Intent State Builder

将事件转为长期意图状态、belief、activation prior。

3 Policy Planner

选择本次生成应采用的 intent policies。

4 Generation

编排 hands、工具、检索、输出结构。

5 Evaluator Ensemble

评估意图覆盖、相关性、时效性、决策价值。

6 Reward Ledger

记录每个 episode 的奖励和诊断。

7 Credit Assignment

判断奖励应归因给 intent、policy、hand 或 prompt。

8 Policy Update

更新权重、失败模式、激活先验和策略钩子。

3. 核心对象模型

IntentState

长期用户意图的结构化状态，不只是文字描述。

{
  "intent_id": "content.fresh_event_judgement",
  "belief": 0.82,
  "activation_prior": 0.71,
  "decay": "slow",
  "domains": ["research", "writing"],
  "policy_hooks": ["retrieve_recent_context", "add_event_judgement"],
  "failure_modes": ["overuses stale news", "adds irrelevant events"],
  "reward_history": []
}
IntentPolicy

可执行策略，而不是 prompt 片段。

{
  "policy_id": "policy.add_fresh_context",
  "when": ["intent_active:fresh_event_judgement"],
  "actions": [
    "retrieve_recent_context",
    "ask_domain_hand_for_event_impact",
    "require_output_section:recent_event_judgement"
  ],
  "reward_targets": ["freshness", "relevance", "decision_usefulness"],
  "weight": 0.64
}
RewardSignal

来自显式反馈、隐式行为和自动 evaluator。

{
  "episode_id": "ep_20260609_001",
  "overall_reward": 0.76,
  "intent_rewards": {
    "content.fresh_event_judgement": 0.91,
    "risk.reversal_condition": 0.43
  },
  "diagnosis": "Fresh context useful; risk section too generic."
}
CreditAssignment

把结果质量归因到具体策略和组件。

{
  "episode_id": "ep_20260609_001",
  "policy_updates": [
    {
      "policy_id": "policy.add_risk_countercase",
      "weight_before": 0.62,
      "weight_after": 0.54,
      "reason": "Activated but produced generic risk framing."
    }
  ]
}

4. 为什么用 Contextual Bandit，而不是完整 RL

方案 优点 问题 建议
Prompt + Memory 实现快，容易调试 没有奖励和归因，无法学习策略质量 保留为输入层，不作为核心 harness
Contextual Bandit 每次生成都是一次可评估 episode，适合产品交互 不处理复杂多步长期回报 第一阶段推荐
Full RL 理论上可优化长期策略 需要大量 episode、稳定环境和明确 reward 暂不直接上，后续可演进

5. Evaluator Ensemble

生成完成后自动运行多评估器，避免只依赖用户显式反馈。

IntentCoverageEvaluator

检查激活 intent 是否被实际满足。

RelevanceEvaluator

检查是否强行塞入无关长期偏好。

FreshnessEvaluator

需要时效信息时，检查是否检索并使用近期上下文。

DecisionUsefulnessEvaluator

判断输出是否提高决策质量，而非只增加内容。

UserStyleEvaluator

检查粒度、表达和结构是否符合用户偏好。

DomainEvaluator

由 domain pack 提供，例如投资研究、写作、代码审查。

6. 可视化：从天赋点到策略面板

8. 分阶段落地路线

阶段 目标 交付物
Phase 1 从 Intent Wiki 升级为 IntentStateStore 状态对象、belief、activation prior、failure modes
Phase 2 引入 PolicyPlanner policy schema、激活策略、prompt/tool/hand hooks
Phase 3 引入 Evaluator Ensemble intent coverage、freshness、relevance、decision usefulness evaluator
Phase 4 引入 Reward Ledger 与 Credit Assignment episode log、reward log、policy weight update
Phase 5 升级可视化 天赋图 + 策略面板 + reward 归因视图

9. 架构原则

  • 核心 harness 必须通用，投资研究只是 domain pack。
  • 事件流是证据，不是长期意图本身。
  • 长期意图必须有 belief、reward history、failure modes 和 activation policy。
  • 生成时必须显式记录采用了哪些 intent 和 policy。
  • 生成后必须评估，而不是假设 prompt 注入就代表满足意图。
  • 奖励更新必须可解释，避免隐藏式用户画像。
