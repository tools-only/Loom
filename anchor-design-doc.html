一需求分析

1.1 思考起点

项目最初的构想是基于一个观察:Anthropic 提出大模型生成 HTML 比 Markdown 更易于可视化和交互。在此基础上,设想做一个 AI-native 的浏览器,把 AI 封装在浏览器内部,实现两件事:

  • AI 生成的内容直接实时渲染在浏览器页面,这个页面不是传统的静态 page,而是一个支持选择和编辑的活页面
  • 用户可以在页面上实时编辑,也可以选中区域唤起 AI 进行局部修改

1.2 自我审视:三个根本问题

问题一 · 不面向未来

未来 base model 必然会强大到足以取代传统浏览器的角色。实时渲染一个页面可能只需要一个简单的 Claude Code hook 即可实现。在经典浏览器架构上嵌入 AI,工程繁琐、价值有限,且很快会被更强的 base model 替代。

问题二 · 不够灵活

渲染一个页面是否真的只能通过浏览器?AI 本身能否实现?AI 生成 HTML 是否就是另一种实现?最初的设想被传统软件架构限定了想象空间。

问题三 · 面向人,而非面向 AI

项目真正的价值,不在于"如何让 AI 输出更好看",而在于:

为用户提供 prompt 以外的交互通道(鼠标选择、框选、拖拽等多样化输入),同时为 AI 提供一个易处理的人类输入接口——把"丰富但模糊"的人类输入,翻译成 AI 擅长处理的结构化数据(CLI、命令行、代码、结构化文本)。

1.3 项目定位

Core Definition
Anchor 是一个轻量化的双向交互界面层。AI 通过它把复杂输出可视化、可读化、可操作化地呈现给用户;用户通过它把鼠标行为、选区、编辑等非 prompt 输入,转化为 AI 易处理的结构化指令。

明确不是什么:

  • 不是 Dify / Coze 这类 agent 配置或工作流编排工具
  • 不是在传统浏览器上叠加 AI 的"AI 浏览器"
  • 不是面向开发者的 AI 应用框架
  • 不自建渲染引擎、不需要数据库、不引入重型 SDK

1.4 核心需求与设计原则

R1 · 轻量化

基于 Claude Code hook 等现成机制即可实现。核心只有一个协议、一个桥、一份 HTML 约定。无后端、无数据库、无自研渲染器。

R2 · 实时性

AI 生成内容流式渲染,用户看到部分内容时即可交互;局部修改不重生成全部;每次回环响应在秒级。

R3 · 双向 Interface

A 方向:AI 为用户提供直观、高可读的可视化。
B 方向:用户的交互行为为 AI 提供细粒度任务推进方向和反馈信号。

R4 · 共享底物

A 和 B 必须建立在同一份数据表示上(本方案选 HTML)。用户操作能直接对应到 AI 生成的代码/数据上,没有解释损耗。

R5 · 通用性

同一套协议覆盖代码生成、股票分析、auto-research 等不同复杂任务。差异性体现在 widget 层,核心 anchor 协议保持稳定。

R6 · 数据反哺

因为 B 把用户行为结构化,每次交互都自动产出高质量数据,可用于 RL/偏好学习/微调专用 patch 模型。

二总体设计

2.1 核心洞见

HTML 既是 A 的渲染产物,也是 B 的可操作底物。

这个等价关系一旦建立,整个系统就被压扁了:

  • AI 生成 HTML(带语义 anchor 标注)→ 这是用户看到的界面 (A)
  • 用户对 HTML 元素的任何交互,被序列化为"HTML 上的操作"
  • 这个操作既能驱动前端渲染反馈,又能直接喂回 AI——因为 AI 本来就是生成这段 HTML 的人,它读得懂 (B)

人和 AI 共享 HTML 这一份语言,不需要中间翻译层。这也是为什么不需要重建一份 Typed Graph 内核——HTML + 一组 data-* 约定,本身就是充分的数据模型。

2.2 双向 Interface 的具体形式

A 方向 · AI 制造可读化界面

  • AI 输出 HTML,内嵌 data-anc="..." 标记每个语义单元
  • 内嵌 data-handles="..." 声明该单元支持哪些操作
  • 浏览器原生渲染 + 前端 JS 注入浮动控件 = 用户看到的可交互界面

B 方向 · 界面制造 AI 可读指令

  • 用户的每个鼠标/键盘行为,被 JS 序列化为 JSON op
  • op 引用 HTML 中的 anchor id,等价于一条 CLI 命令
  • 桥接层把 op 拼成 prompt 续给 AI,AI 返回 HTML patch

整个系统是一个 HTML ↔ op ↔ HTML 的闭环。

2.3 数据基建作为副产物

每个 session 自然产出可用于训练的数据:

  • (html_state, user_op) — 用户行为分布
  • (html_state, op_chain, final_state) — RLHF 风格的纠错轨迹
  • (state, op, ai_patch) — 条件生成训练对
  • 隐式信号:用户反复修改 vs. 一次接受 → 质量打分

这些数据是自然产生、无需标注的,这是本项目相对其他 AI 应用的独特价值。

四协议设计

4.1 HTML 端约定(Anchor 协议)

Claude 生成 HTML 时,按需添加三个 data-* 属性:

<section data-anc="findings"
         data-handles="expand,refine,lock"
         data-deps="data-1,data-2">
  <h2>主要发现</h2>
  <p data-anc="findings.summary"
     data-handles="refine,shorten,longer">
    营收同比增长 23%...
  </p>
</section>
  • data-anc — 唯一 id,跨轮次稳定,作为 AI 与用户的共享指针
  • data-handles — 该元素支持的操作集合,前端据此渲染浮动控件
  • data-deps — 依赖声明,用于级联更新提示和 diff preview

4.2 用户操作 Op 格式

任何鼠标/键盘行为都被前端 JS 编码为一个 JSON op:

{
  "op": "refine",
  "target": "findings.summary",
  "args": { "instruction": "更口语化一点" },
  "context_html": "<p>...原文片段...</p>",
  "selection": { "text": "同比增长 23%", "range": [12, 19] }
}

核心 op 集合(MVP 推荐):

Op语义触发示例
refine对元素局部修改点 handle → 输入修改指令
lock锁定,后续重生成绕开右键菜单 → 锁定
expand展开细节点折叠按钮
shorten / longer调整长度拖滑块或点按钮
edit用户直接编辑文本contenteditable + diff 上报
annotate附加批注/约束/示例选区 → 右键添加备注
branch生成替代方案并排比较"再来一版"按钮
restructure修改骨架(增删元素)拖拽 / 删除区块

4.3 一次完整回环示例

  1. 用户问"分析这只股票"
  2. AI 流式生成 HTML,含 <section data-anc="valuation"> 等多个区块
  3. Webview 渲染,在每个 section 旁渲染浮动控件
  4. 用户点 valuation 旁的"重算"按钮,输入"贴现率改 8%"
  5. JS 发出 op:{op:"refine", target:"valuation", args:{instruction:"贴现率改 8%"}}
  6. Bridge 把 op + 当前 HTML 上下文拼成 prompt 续给 Claude
  7. Claude 返回 valuation 区块及其依赖区块的新 HTML
  8. Bridge 通过 WebSocket 推回,JS 替换对应 DOM 节点
设计要点
整个回路里,用户的鼠标点击经过 JS 编译成 op,等价于一条 CLI 命令。AI 不需要"理解 GUI 意图",它只需要执行一条结构化指令。这就是 R3(双向 interface)落到协议层的具体形式。

五通用交互语法

5.1 八个领域无关的原语

不论代码、股票、研究,任何带 anchor 的节点都支持下列原语:

原语含义
Inspect展开元素,查看其 lineage、依赖、不确定度
Refine对元素做局部修改(自然语言或带参数)
Lock锁定元素,后续重生成绕开它
Annotate附加约束、批评或示例;批注以可视 pill 形式挂在元素旁
Branch对元素生成替代方案,并排比较
Connect在两个元素之间手动添加边(声明依赖或对比)
Restructure修改骨架本身(增删骨架节点、移动子树)
Replay沿 lineage 回到上游某点,从那里重生成下游

5.2 类型化 Handles

每种语义元素再额外提供 type-specific 控件,但触发方式与原语保持一致(节点旁的浮动控件,不需要打字):

  • 代码文件节点:重构、加测试、提取函数、改名
  • 财务指标节点:敏感度分析、换假设、换时间窗口
  • 研究假设节点:找反例、找证据、调整置信度
  • 文本段落节点:换语气、改长度、列出要点

六跨任务适配

同一份 anchor 协议在不同复杂任务下的具体落地:

6.1 代码生成

  • 容器:HTML 内嵌 Monaco / CodeMirror 渲染代码
  • Anchor 粒度:文件 / 类 / 函数级
  • 默认视图:项目树视图,新增/修改文件高亮(绿色 = 新增,黄色 = 修改),旁标 diff 摘要
  • 典型 op:{op:"refine", target:"auth.py#login", args:{instruction:"改成 OAuth2"}}
  • 级联:AI 通过 data-deps 知道 auth.py#login 的依赖,自动重生成相关测试和调用方

6.2 股票分析

  • 容器:仪表盘风格 HTML,KPI 卡 + 图表 + 章节
  • Anchor 粒度:公司画像 / 财务 / 估值 / 风险各区块,以及关键指标
  • 默认视图:多卡片布局 + 关键图表
  • 典型 op:拖动"贴现率"滑块 → 估值区块及依赖结论实时重算
  • 锁定:用户 Lock"行业判断"区块,后续改其他参数时此区块保持不变

6.3 Auto-Research

  • 容器:假设地图(树状)+ 证据链(时间线)双视图
  • Anchor 粒度:问题 / 假设 / 证据片段 / 反例 / 结论
  • 默认视图:假设节点带置信度颜色编码
  • 典型 op:点假设节点 → "找反例",AI 在子树下新增反例节点
  • Annotate:用户在某证据上加"质量低,样本太小",对应假设置信度自动降级

6.4 边界与扩展机制

HTML 适合"可读性强的结构化输出"。对于纯代码或纯数据型任务,通过约定 data-anc-kind 扩展,前端用专用 widget 渲染——但 anchor id 和 op 协议保持统一:

<div data-anc="auth-module" data-anc-kind="code">
  <!-- 前端用 Monaco 渲染 -->
</div>

<div data-anc="revenue-trend" data-anc-kind="chart">
  <!-- 前端用 ECharts/Recharts 渲染 -->
</div>

HTML 是"容器协议",里面可以挂任何 widget(代码编辑器、表格、图表、3D 等),但共享同一套 anchor id 和 op 语法。这是项目通用性的关键。

七数据基建价值

7.1 自动收集的数据形式

每条用户交互天然产生一条结构化记录:

{
  "html_before": "...",      // 交互前的 HTML 状态
  "user_op": {...},          // 用户做了什么
  "html_after": "...",       // AI 回应后的状态
  "latency_ms": 1240,
  "user_kept": true,         // 用户是否保留了这次修改
  "follow_up_ops": [...]     // 后续连续操作
}

由此可派生:

  • 偏好数据:同一 op 下用户在多个候选中选择了哪个
  • 纠错数据:用户对 AI 输出主动做了什么修改
  • 行为序列:用户在什么场景下倾向做什么连续操作
  • 质量信号:连续 refine 三次 vs. 一次接受 → 隐式打分

7.2 应用方向

UI Patch Model

训练专用小模型:输入 HTML + op,输出 patch。逐步替代部分大模型调用,降本提速。

偏好对齐

用 RLHF / DPO 训练对齐用户审美与表达偏好,让 AI 的默认输出更符合期待。

行为预测

预测用户下一步操作,预先生成候选,做到"还没点就已经准备好"。

领域知识沉淀

不同领域(代码/金融/研究)的高质量交互轨迹,可作为该领域的高价值微调语料。

八MVP 实施计划

8.1 两周时间表

阶段内容产出
Day 1-2 编写 CC hook,把 Claude 输出转成带 anchor 的 HTML;搭建最简 Webview 验证流式渲染 HTML 能流式渲染到浏览器
Day 3-5 Webview 注入通用 JS,给带 data-handles 的元素加浮动控件;打通点击 → console 输出 op Op 格式定型,前端交互捕获就绪

8.2 MVP 验证目标

  • HTML anchor 协议能否不修改地复用到两个不同领域
  • 典型局部 op 能否在 2-3 秒内完成回路(用户感知"实时")
  • 用户行为日志能否形成可用于训练的结构化数据集
  • 核心代码量是否控制在千行级别(轻量化目标)

九边界、风险与未来扩展

9.1 适用边界

适合

有结构、可分块、可局部修改的任务:研究报告、数据分析、文档型代码 review、规划与决策类任务、auto-research 流程。

不适合

开放式讨论、纯创意闲聊、需要长上下文连贯生成的内容(用普通对话 UI 更合适)。

9.2 主要风险

风险缓解策略
HTML 协议在某些任务表达力不够用 widget 容器化(data-anc-kind 扩展机制)
局部重生成破坏全局一致性通过 data-deps 声明 + diff preview 让用户预览级联影响后再执行
Anchor id 跨轮次稳定性由 AI 显式维护;监控 id 漂移率;必要时加入 diff 工具自动迁移
用户学习成本(handles 怎么用)handles 是渐进式可见的;按需 hover 出现;不强迫用户学
被更强 base model 直接取代协议本身极简,可作为任何 base model 的输出格式;且数据资产是独立价值

9.3 长期方向

  • 协议标准化:开放 anchor 协议,允许第三方写 widget(代码、图表、3D、视频等)
  • 专用 patch 模型:用积累的数据训练小模型,替代部分 LLM 调用
  • 可视化操作历史:把 op 流变成可回放/分支的历史,用户可以"撤销并尝试另一条路径"
  • 多人协作:多个用户和多个 AI agent 同时在一份 HTML 上工作,光标共享、约束合并
  • 跨 session 记忆:用户偏好与领域知识从历史数据中自动沉淀,新 session 直接受益
一句话总结
Anchor 不发明新轮子。它做的事是:让 HTML 既当窗户又当语言,让 GUI 行为编译成 CLI,让人和 AI 用同一种东西交流;由此把"AI 给人看"和"人给 AI 说"统一成一个闭环,顺带把这个闭环本身变成持续产出数据的 infra。
